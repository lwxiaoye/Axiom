# AXIOM 生产部署手册

本文描述**当前这台单机服务器**（clinirag.top）上 AXIOM 的部署方式。2026-09-18 按仓库内的
`docker-compose.local.yml`、`docker-compose.server.yml`、`docker-compose.dev.yml`、
`deploy/redeploy.sh`、`deploy/dev-server.sh`、`deploy/frontend/Dockerfile.prebuilt`、
`agent-api/.env.example`、`auth-api/` 逐项核对；文中所有命令都能在这些文件里找到出处。
没有核对过的步骤一律写成「见 xxx 文件」，不在本文替它下结论。

原 JeecgBoot Java 后端已下线，APISIX、New API、独立 websearch-api/ocr-api/browser-api 等旧组件
都不再参与本机部署（见第 7 节）。旧版手册中关于 Java、APISIX forward-auth、`GATEWAY_IDENTITY_*`
的内容已全部作废。

> 所有密钥、口令都在被 Git 忽略的 `deploy/local/.env` 里。本文只写变量名，不写值；
> 不要把该文件的内容复制进文档、Shell 历史或提交。

## 1. 架构与端口

### 1.1 主机

| 项目 | 事实 |
| --- | --- |
| CPU / 内存 / 磁盘 | 1 vCPU / 2.9 GB / 24 GB（与其它应用共用，磁盘长期在 90% 上下） |
| 容器编排 | Docker Compose v2，项目名 `axiom`（`docker-compose.local.yml` 顶部 `name: axiom`） |
| 宿主机工具链 | Node 22、pnpm 10.15.1、docker-buildx（`deploy/frontend/Dockerfile.dockerignore` 需要 BuildKit） |
| 公网入口 | 宿主机 nginx + Let's Encrypt，站点配置 `/etc/nginx/conf.d/clinirag.top.conf`（**不在仓库内**） |

### 1.2 请求链路

```text
浏览器 ──HTTPS──> 宿主机 nginx（clinirag.top，仓库外）
                     │  /  与 /agent-api/ 都反代到 127.0.0.1:3200
                     ▼
              axiom-frontend（nginx:1.28-alpine，deploy/frontend/nginx.conf）
                     │  /api/*   去掉 /api 前缀 → auth-api:9090
                     │  /upload/* → auth-api:9090
                     │  /agent-api/* 保留前缀 → agent-api:8000（关闭缓冲，SSE）
                     ▼
        ┌────────────┴────────────┐
   axiom-auth-api            axiom-agent-api / axiom-agent-worker
   (登录、注册、token、用户)     (对话、内置智能体、知识库、Skill、文件)
   SQLite 卷 axiom_auth_data        │
                                    ├─ mysql:8.4（ai_boot）
                                    ├─ postgres:15（langgraph_checkpoints / agent_runtime）
                                    ├─ qdrant v1.9.7
                                    ├─ searxng（联网搜索）
                                    ├─ agent-browser（Playwright MCP）
                                    ├─ opensandbox-server（代码沙箱，跑 agent-sandbox-py:local）
                                    └─ 对话/向量/重排模型：管理配置页里填的云端 OpenAI 兼容地址
```

`agent-api` 用 `X-Access-Token` 回源 `AUTH_API_BASE=http://auth-api:9090` 的
`/sys/user/getUserInfo` 校验身份（`agent-api/app/core/auth.py`），`AUTH_TOKEN_CACHE_TTL_SECONDS`
在 compose 里固定为 `0`，即每次请求都重新校验。

### 1.3 服务清单（`local` + `server` 叠加后）

| 服务 | 容器名 | 镜像 / 构建 | 宿主机端口 | 说明 |
| --- | --- | --- | --- | --- |
| frontend | axiom-frontend | `deploy/frontend/Dockerfile.prebuilt`（只打包宿主机构建好的 `dist/`） | `127.0.0.1:3200` | 健康检查 `GET /healthz` |
| auth-api | axiom-auth-api | `auth-api/Dockerfile` | 无（dev 叠加时 `127.0.0.1:9090`） | 健康检查 `GET /health` |

### 1.4 `deploy/local/.env` 变量名

compose 只通过这一份文件做插值。带 `:?` 的是缺了就起不来的：

| 变量 | 用途 | 必填 |
| --- | --- | --- |
| `AXIOM_DB_PASSWORD` | MySQL root/axiom 与 PostgreSQL axiom 的口令 | 是 |
| `AXIOM_ADMIN_USER` / `AXIOM_ADMIN_PASSWORD` | auth-api 内置管理员（口令至少 12 位，`CHANGE_ME` 会拒绝启动） | 口令必填 |
| `AXIOM_CONNECTOR_SECRET` | 注入为 `CONNECTOR_SECRET_KEY`：连接器凭据、对话模型/重排模型密钥的 Fernet 主密钥。留空时 agent-api 会在容器内 `data/.connector_key` 自生成一把，该路径不在卷里，重建容器后已存密文将解不开 | 实际必填 |
| `AXIOM_OPENSANDBOX_API_KEY` | opensandbox-server 与 agent-api 共用的沙箱 API key | 是 |
| `AXIOM_SEARXNG_SECRET` | SearXNG 的 `SEARXNG_SECRET` | 是 |
| `AXIOM_MODEL_BASE_URL` | 注入为 `NEWAPI_BASE_URL`，OpenAI 兼容模型网关地址（本机为另一套 compose 里的 grok2api，见 3.3） | 无默认值 |
| `AXIOM_INITIAL_CHAT_MODELS` | 空表时初始化 `ai_chat_model` 模型目录，逗号分隔，第一个为默认 | 否 |
| `AXIOM_EMBEDDING_MODEL` / `AXIOM_EMBEDDING_DIMENSION` | `DEFAULT_EMBEDDING_MODEL` / `DEFAULT_EMBEDDING_DIMENSION` 的默认值（缺省 `text-embedding-v4` / `1024`） | 否 |
| `AXIOM_MODEL_AUDIT_TIMEOUT_SECONDS` | 模型用量审计每个阶段的写库预算（缺省 `2.5`；代码缺省 0.75 是按多核机器定的，1 核机器负载一高就丢审计行） | 否 |
| `AXIOM_SEARXNG_ENGINES` | SearXNG 缺省引擎（缺省 `brave,google,360search`；bing 在当前镜像里解析失效，duckduckgo/qwant/baidu 对该 IP 出验证码；管理页保存过的以页面为准） | 否 |
| `AXIOM_FIRECRAWL_URL` | 只在开了 `firecrawl` profile 时填 | 否 |
| `AXIOM_SANDBOX_MEMORY` / `AXIOM_BROWSER_MEM_LIMIT` | 沙箱内存（缺省 `512Mi`）、浏览器容器内存（缺省 `1g`） | 否 |
| `AXIOM_LOGIN_AES_KEY` / `AXIOM_LOGIN_AES_IV` / `AXIOM_REQUEST_SIGNATURE_SALT` | 登录协议的公开 AES/签名参数，前端构建期与 auth-api 必须一致；改了要重建前端 | 有默认值 |
| `AXIOM_LOCAL_DEMO_LOGIN` / `AXIOM_LOCAL_DEMO_USERNAME` / `AXIOM_LOCAL_DEMO_PASSWORD` | 演示模式与登录框预填（会进浏览器包） | 否 |
| `AXIOM_CORS_ORIGINS` | auth-api 允许的来源 | 有默认值 |

模板见 `deploy/local/.env.example`；agent-api 直接以 `.env` 运行时的完整变量名见
`agent-api/.env.example`。

## 2. 首次部署

以下步骤合成自 `README.md`「本地 Docker」、`docker-compose.server.yml` 头部注释和
`deploy/redeploy.sh`。本机已经部署完成，这一节是给重装或迁机用的。

```bash
cd /root/axiom
# 1) 私有配置
cp -n deploy/local/.env.example deploy/local/.env
#    编辑 deploy/local/.env：至少填 1.4 节里标「是」的变量，把所有 CHANGE_ME 换掉

# 2) 宿主机前端依赖（前端构建必须在宿主机，见 3.2）
pnpm install --frozen-lockfile

# 3) 构建 dist + 全部镜像并拉起（脚本会先停容器、配 zram、逐个构建、回收缓存）
./deploy/redeploy.sh all
```

`redeploy.sh` 最后会执行 `docker compose ... up -d` 并轮询 `http://127.0.0.1:3200/healthz`。
之后手工确认：

```bash
COMPOSE="docker compose --env-file deploy/local/.env -f docker-compose.local.yml -f docker-compose.server.yml"
$COMPOSE ps
curl -fsS http://127.0.0.1:8000/health/ready
curl -fsS http://127.0.0.1:3200/healthz
```

数据库迁移：compose 把 `MIGRATE_ON_STARTUP` 固定为 `"true"`，agent-api 启动时自己建表/补列，
首次部署不需要手工跑 Alembic。它的适用范围和「旧库升级必须先走正式迁移」的限制见
`agent-api/migrations/README.md`。

宿主机 nginx 与证书不在仓库内：把 `/` 和 `/agent-api/` 反代到 `127.0.0.1:3200`
即可（本机现状是 `/etc/nginx/conf.d/clinirag.top.conf`，`/agent-api/` 那段关了
`proxy_buffering`、`proxy_read_timeout 600s` 以支持 SSE）。仓库里的 `deploy/nginx_conf`
是 Java/APISIX 时代的样例，**不要**拿它覆盖现网配置。

登录：默认用户名 `AXIOM_ADMIN_USER`（缺省 `admin`），口令 `AXIOM_ADMIN_PASSWORD`，需要图形验证码。
auth-api 也开放了 `POST /sys/user/register`（带验证码的自助注册）。

## 3. 日常更新（`deploy/redeploy.sh`）

```bash
cd /root/axiom
./deploy/redeploy.sh frontend   # 改了前端：重建 dist + 换 frontend 镜像
./deploy/redeploy.sh backend    # 改了 agent-api / auth-api：重建两个后端镜像
./deploy/redeploy.sh all
```

脚本做的事（按顺序，都在脚本里）：

1. `frontend` / `all`：`docker compose stop` 停掉**所有**容器，释放内存。
2. `ensure_zram`：把 `/dev/zram0` 配成 6 GiB、`zstd`、swap 优先级 100，并设
   `vm.page-cluster=0`、`vm.swappiness=100`；`drop_caches`。
3. 从 `deploy/local/.env` 导出 `VITE_LOGIN_AES_*`、`VITE_REQUEST_SIGNATURE_SALT`、`VITE_LOCAL_DEMO_*`，
   然后 `NODE_OPTIONS=--max-old-space-size=4096 vite build`，接着 `esno ./build/script/postBuild.ts`、
   `node scripts/bust-theme-css.mjs`。
4. `docker compose build frontend`（`Dockerfile.prebuilt` 只是把 `dist/` 拷进 nginx 镜像）。
5. `backend`：`build auth-api` → `build agent-api` **逐个**构建，避免并行吃爆内存；
   agent-worker 复用 agent-api 镜像，不单独构建。
6. `docker builder prune -f`、`docker image prune -f`：24 GB 磁盘曾因构建缓存占满导致 MySQL 建表失败。
7. `docker compose up -d`；`ensure_grok_network` 把 grok2api 容器幂等接入 axiom 网络（见 3.3）；
   轮询 `/healthz`；`docker compose ps`。

### 3.1 只改了后端代码

不需要重建前端：`./deploy/redeploy.sh backend`。`backend` 分支**不会**先停容器，
但两个镜像仍是串行构建。如果只是想让改动即时生效而不重建镜像，用第 4 节的开发叠加。

### 3.2 前端构建的硬约束（已实测）

前端在这台机器上默认构建**必然 OOM**，下面四条缺一不可，`redeploy.sh frontend` 已经全部编码进去：

1. **必须在宿主机构建，不能在 Docker 里构建**——`docker-compose.server.yml` 把 frontend 的
   Dockerfile 换成了 `Dockerfile.prebuilt`，容器里没有 Node。
2. **先停所有容器**：10 个服务常驻约 1.1 GB，不停就会把 node 立刻挤进 swap。
3. **zram 6 GiB zstd 作 swap**，不能溢出到磁盘 swap：溢出后是几十 GB 的换页抖动，
   曾有一次跑了 2 小时 23 分都没结束。
4. **`--max-old-space-size=4096`**：8192 超物理内存 2.7 倍直接死，5120 抖动，2800 在 transform 阶段 OOM。

一次成功的构建约 **41 分钟**。构建期间站点不可用（容器已停）。

**不要为了省内存开 tree-shaking。** `vite.config.ts` 里 `treeshake: false` 是仓库默认且刻意：
Rollup 要做除屑必须保留完整 AST 和作用域分析，打开后反而在 transform 阶段更早 OOM，已实测并回退。

### 3.3 对话模型网关（grok2api）

`AXIOM_MODEL_BASE_URL` 指向的 grok2api 属于另一套 compose，只发布在宿主机回环端口上；
agent-api 要按容器名访问它必须与之同网。`docker network connect` 是运行时操作，grok2api
重建后会丢失，所以 `redeploy.sh` 每次都幂等地重连一次（`ensure_grok_network`）。若手工
`up -d` 而没跑脚本，发现模型不可达时先检查这一步。

## 4. 开发模式（`docker-compose.dev.yml` + `deploy/dev-server.sh`）

在服务器上直接改代码时叠加第三份 compose：

```bash
cd /root/axiom
docker compose --env-file deploy/local/.env \
  -f docker-compose.local.yml -f docker-compose.server.yml -f docker-compose.dev.yml up -d
./deploy/dev-server.sh --daemon     # 或不带参数前台运行，Ctrl-C 停止
```

`docker-compose.dev.yml` 改了什么：

| 服务 | 变化 |
| --- | --- |
| frontend | 进 profile `packaged`，`up` 时不启动；页面改由宿主机 Vite dev server 提供 |
| auth-api | 发布 `127.0.0.1:9090`（Vite 代理要直连它）；`app.py`、`store.py` 只读挂进容器；`uvicorn --reload` |
| agent-api | `./agent-api/app` 只读挂到 `/app/app`；`uvicorn --reload --reload-dir /app/app`（镜像里 `uvicorn[standard]` 自带 watchfiles，走 inotify） |
| agent-worker | **同样挂 `./agent-api/app`**——它和 agent-api 共用镜像，只重建/重启 agent-api 抓不到它；改完 `docker compose ... restart agent-worker` |

`deploy/dev-server.sh` 做的事：

- `NODE_OPTIONS=--max-old-space-size=1536`，`vite --host 127.0.0.1`（`AXIOM_DEV_BIND` 可改），端口来自 `.env` 的 `VITE_PORT=3200`。
  dev server **只监听回环**，公网仍经宿主机 nginx + HTTPS 反代到 3200，与生产同一入口。
- `VITE_DEV_PUBLIC_HOST`（缺省 `clinirag.top`）：`vite.config.ts` 据此把 HMR 配成
  `{ protocol: 'wss', host: <域名>, clientPort: 443 }`，否则浏览器会去连 `127.0.0.1:3200` 而失败。
- `--daemon` 时 `nohup` 后台运行，日志在 `/root/axiom/dev-server.log`。
- Vite 代理规则在 `.env.development` 的 `VITE_PROXY`：`/api` → `127.0.0.1:9090`，
  `/upload` → `127.0.0.1:9090/upload`，`/agent-api` → `127.0.0.1:8000/agent-api`。

`vite.config.ts` 已把 `**/.claude/**` 排除出文件监听，并行会话的 worktree 不会触发整页 reload。

回到容器化部署：去掉 `-f docker-compose.dev.yml`，停掉 dev server，再按第 3 节
`redeploy.sh frontend` 重新打包前端镜像。

## 5. 管理配置

登录后点右上角头像 → **管理配置**（只有带 `admin:manager` 权限的账号能看到，
auth-api 内置管理员默认有）。它在新标签页打开 `/admin`
（`src/views/peopleCenter/pages/AdminConsolePage.vue`），左侧五个板块：

| 板块 | 内容 | 后端接口（`/agent-api` 前缀） | 密钥存储 |
| --- | --- | --- | --- |
| 对话模型 | 名册：多条模型（名称 / OpenAI 地址 / Anthropic 地址 / 模型 ID / 密钥 / 启用），设默认、拖动排序、逐条「测试连接」与「测速」；「启用平台模型」总开关；对全员生效，用户可在 `/center/models` 填个人覆盖 | `GET/PUT /model-connection`，`POST /model-connection/test`、`/test-speed`；个人 `/model-connection/personal*` | 每条 `api_key_cipher`，Fernet 密文入库（`CONNECTOR_SECRET_KEY`）；形状见 [`模型连接配置.md`](模型连接配置.md) |
| 向量模型 | base_url / model / api_key、维度；**更换模型或维度后需要重建索引** | `/embedding-config`、`/embedding-config/test` | `ai_embedding_model.api_key` 列存 Fernet 密文；历史明文行在 agent-api 启动时原地加密（`app/main.py` `_encrypt_embedding_keys`） |
| ↳ 重排模型 | 同页下方：base_url / model / api_key / 启用开关；留空则只按向量相似度排序 | `/rerank-config`、`/rerank-config/test` | `api_key_cipher`，Fernet 密文入库 |
| 联网搜索 | 启用开关、引擎、「结果重排」（不重排 / 平台重排模型）等 | `/platform-config/web-search`、`.../test` | 接口返回时密钥字段置空并带 `secrets_set` 标记，保存时空字段保留库中原值 |
| 校园百事通 | 选择已启用的对话模型、编辑草稿、校验、发布；发布后用户侧即刻生效 | `/campus-assistant/admin/config`、`.../draft`、`.../draft/validate`、`.../draft/publish` | 无密钥 |
| 用户 | 列出内置管理员 + 自助注册用户（用户名 / 姓名 / 角色），只读 | auth-api `GET /sys/user/list` | — |

页面上 `api_key` 留空表示「保持原密钥」，GET 只返回 `has_api_key`，不回显明文。

env 与页面的关系：`docker-compose.server.yml` 里的 `NEWAPI_BASE_URL`、`DEFAULT_EMBEDDING_*`、
`WEB_SEARCH_SEARXNG_ENGINES` 等只是**缺省值**；管理页保存过之后以页面为准
（`docker-compose.server.yml` 注释与 `WEB_SEARCH_SEARXNG_ENGINES` 旁的说明）。

## 6. 已知限制

- **单机、无冗余。** 前端构建期间必须停掉全部容器，站点中断约 41 分钟；改前端请挑低峰。
- **磁盘紧张。** 24 GB 盘常年 90% 以上；`redeploy.sh` 每次构建后都 prune，仍要定期看 `df -h /`。
  不要 `docker compose down -v`，数据全在命名卷里（`axiom_mysql_data`、`axiom_pg_data`、
  `axiom_qdrant_data`、`axiom_auth_data`、`axiom_opensandbox_state`）。
- **firecrawl 网页抓取默认关闭**（profile `firecrawl`），联网搜索只有 SearXNG 检索；
  升配后 `--profile firecrawl` 再开，并填 `AXIOM_FIRECRAWL_URL`。
- **搜索引擎受 IP 限制。** bing 在当前 SearXNG 镜像里解析失效，google/baidu 对该 IP 出验证码，
  缺省只留 duckduckgo、brave。
- **浏览器工具是官方精简镜像**（chromium headless shell）。仓库里 `deploy/browser-api/Dockerfile`
  基于的 `playwright:*-noble` 约 4.5 GB，装不下。
- **agent-api 用的是 `Dockerfile.local`**，不含 LibreOffice；Office 文档转换见 `agent-api/Dockerfile`
  与 `README.md` 的说明，本机未启用。
- 所有模型密钥（对话 / 向量 / 重排）均 Fernet 密文入库，密钥来自 `AXIOM_CONNECTOR_SECRET`；换了它旧密文解不开，需在管理页重填。
- **auth-api 不是完整用户体系**：单管理员 + 自助注册，不支持编辑角色；未实现接口返回 404
  `success=false`（`auth-api/README.md`）。
- **grok2api 与本 compose 的网络连接是运行时状态**，grok2api 重建后要重跑 `redeploy.sh` 或手工
  `docker network connect`（见 3.3）。
- **`MIGRATE_ON_STARTUP=true` 不等于所有版本化迁移都跑过**；旧库升级的正式流程见
  `agent-api/migrations/README.md`「生产 runbook」。启动期只会建缺的表/补缺的列，**不会删**：
  例如 `mysql_0023_drop_skins`（2026-09-19 移除皮肤系统后删 7 张表与 1 列）、
  `mysql_0024_drop_orchestration` 与 `runtime_0024_drop_eval_runs`（2026-09-19 删除工作流编排/子智能体/
  对外 Agent API 后删 13 张 MySQL 表与 1 张 Runtime 表）就得手工跑（两条链各跑一次 `upgrade head`）。容器里的
  `/app/migrations` 来自镜像，dev 模式下要把检出挂进去跑：
  `docker run --rm --network axiom_default --env-file <库连接 env> -v "$PWD/agent-api:/app" -w /app axiom-agent-api alembic -c migrations/alembic.ini -n mysql upgrade head`。

## 7. 仓库里不参与本机部署的目录

这些目录是旧架构或独立部署材料，本机 compose 没有引用，保留只为溯源：

| 目录 | 状态 |
| --- | --- |
| `deploy/apisix` | APISIX 官方示例（路由 `/get → web1:80`），本机没有 APISIX，agent-api 也已删掉网关签名身份路径 |
| `deploy/newapi` | New API 模型网关的独立 compose，本机用 grok2api 代替 |
| `deploy/browser-api` | 自建 Playwright 镜像，本机改用 `mcr.microsoft.com/playwright/mcp` 官方镜像 |
| `deploy/ocr-api` | 独立文字识别服务（Paddle）的旧部署材料；本机没有这一层，对话图片直接进多模态模型，扫描件由平台对话模型（视觉）识别（`docker-compose.server.yml` 头注释） |
| `deploy/websearch-api` | 只有 `searxng/settings.yml` 被本机 compose 挂载；其余（firecrawl、reranker）未用 |

| `deploy/nginx_conf` | Java/APISIX 时代的宿主机 nginx 样例，与现网配置无关 |
