# AXIOM AI 平台生产部署手册

本文面向 Linux 服务器部署完整平台。部署前将文中的占位符替换为实际值：`<JAVA_HOST>`、`<AGENT_HOST>`、`<GATEWAY_HOST>`、`<SERVICE_HOST>`、`<SECRET>`。

2026-09-11 按本仓库部署文件与 Agent API 源码核对。本文是生产部署方案，不代表目标服务器已部署或通过验收；日常本机开发仍使用 [`本地热更新开发工作流.md`](本地热更新开发工作流.md) 中的 Vite 与 `run.py`。Java 仓库和服务器实际 Nginx/APISIX 配置不在本次源码核对范围内。

> 不要把生产密码、API Key 或现有 `.env` 原文复制到文档、Shell 历史或 Git。本文只列出需要配置的属性名和示例格式。

## 1. 部署范围与依赖关系

```text
浏览器
  -> 前端/Nginx
  -> APISIX（统一入口、Agent forward-auth）
       -> Java 基础平台（鉴权、知识库、MinIO）
       -> Agent API（智能体、对话、工作流）
            -> New API（模型网关）
            -> Qdrant / PostgreSQL（向量、Runtime）
            -> OpenSandbox（代码执行）
            -> browser-api（真实浏览器）
            -> OCR API
            -> websearch-api（SearXNG + Firecrawl + Reranker）
```

| 范围 | 仓库或目录 | 默认对外端口 | 是否必需 |
| --- | --- | ---: | --- |
| APISIX + etcd | `deploy/apisix` | 9080、9180 | 是 |
| New API + PostgreSQL + Redis | `deploy/newapi` | 3001 | 是 |
| browser-api（Playwright MCP） | `deploy/browser-api` | 8089 | 是 |
| OCR API（PaddleOCR） | `deploy/ocr-api` | 8088 | 是 |
| OpenSandbox | `deploy/opensandbox-api` | 8091 | 是 |
| websearch-api | `deploy/websearch-api` | 8085、8086、8087 | 是 |
| Java + MySQL + Redis + MinIO | 独立 Java 仓库，服务器路径由部署方提供 | 9090、3306、6379、9098、9099（示例） | 是 |
| agent-api + worker + Runtime PG + Qdrant | `agent-api` | 8000、5432、6333 | 是 |
| Ollama + 向量模型 | 独立安装 | 11434 | 否；学校云端向量模型可替代 |

`deploy/opensandbox-api` 与 `agent-api/deploy/opensandbox` 是同一类 OpenSandbox 部署材料。本环境以 `deploy/opensandbox-api` 为准；**不要同时部署两份**，否则会争用同名容器、卷和网络。

## 2. 部署前准备

所有服务端安装 Docker Engine、Docker Compose v2，并确保宿主机能拉取所需镜像。Java 服务额外需要 JDK 17 和 Maven（若在宿主机构建 JAR）；前端构建需要 Node.js 与 pnpm。

建议的最小资源预算：Java/Agent 主机 8 vCPU、16 GB 内存；联网搜索主机 12–16 GB 内存起步；browser-api 默认给 4 GB；OCR 默认给 3 GB。生产上应把 MySQL、Redis、MinIO、PostgreSQL、Qdrant 的数据目录或 Docker volume 纳入备份。

防火墙/安全组只向调用方开放必要端口。`9180`（APISIX Admin）、`3001`（New API 管理端）、`8091`（OpenSandbox）、`8085–8089`（工具服务）、`5432`、`6333`、`6379`、`3306` 不应对公网开放。尤其是 browser-api 的 8089 没有业务鉴权，只能放行 agent-api 主机。

## 3. 建议启动顺序

1. 启动 APISIX、New API，以及 browser/OCR/websearch 等组件服务。
2. 启动 Java 的 MySQL、Redis、MinIO，再启动 Java 基础平台。
3. 启动 agent-api（它会创建 `agent-api_agent-network`）。
4. 启动 OpenSandbox；它依赖上一步创建的网络。
5. 配置 APISIX 路由、New API 渠道、agent-api 的外部服务地址。
6. 启动前端并做端到端验收。

下面所有命令均在相应目录执行，首次部署推荐使用 `docker compose up -d --build`。已稳定运行后，纯配置变更一般使用 `docker compose up -d --force-recreate`；镜像或 Dockerfile 变更才增加 `--build`。

## 4. 组件服务

### 4.1 APISIX 网关

目录：`deploy/apisix`

```bash
cd /srv/Axiom/deploy/apisix
docker compose up -d
docker compose ps
curl -fsS http://127.0.0.1:9180/apisix/admin/services \
  -H 'X-API-KEY: <APISIX_ADMIN_KEY>'
```

必须修改 [`config.yaml`](../deploy/apisix/apisix_conf/config.yaml)：

| 配置项 | 要求 |
| --- | --- |
| `deployment.admin.allow_admin` | 改为运维网段或堡垒机 IP；不可保留 `0.0.0.0/0`。 |
| `deployment.admin.admin_key[*].key` | 使用随机强密钥，并通过受控密钥管理保存。 |
| `apisix.node_listen` | 默认 9080；如被其他网关占用再调整。 |

部署后创建到 Java、agent-api 和 New API 的路由。agent-api 路由必须通过 `forward-auth` 调 Java 的 `/auth/verify`，并只把签名后的用户上下文转发给 agent-api。路由的 upstream 写实际地址，例如 `<AGENT_HOST>:8000`；前端只应访问 APISIX 暴露的路径，而不是直接访问内部服务。

### 4.2 New API 模型网关

目录：`deploy/newapi`

```bash
cd /srv/Axiom/deploy/newapi
# 先修改 docker-compose.yml 中默认数据库/Redis 密码，再启动
docker compose up -d
docker compose ps
curl -fsS http://127.0.0.1:3001/api/status
```

必须修改 [`docker-compose.yml`](../deploy/newapi/docker-compose.yml) 中的以下值，三处数据库密码必须一致：

| 配置位置 | 属性 | 配置内容 |
| --- | --- | --- |
| `new-api.environment` | `SQL_DSN` | New API PostgreSQL 连接串与随机密码。 |
| `new-api.environment` | `REDIS_CONN_STRING` | New API Redis 密码连接串。 |
| `redis.command` | `--requirepass` | 与 `REDIS_CONN_STRING` 相同的 Redis 密码。 |
| `postgres.environment` | `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | 独立的生产账户、强密码和库名。 |
| `new-api.environment` | `SESSION_SECRET` | 多节点部署或生产环境必须设置为随机值。 |

登录 `http://<NEWAPI_HOST>:3001` 后，在管理界面添加模型渠道和令牌。agent-api 的 `NEWAPI_BASE_URL` 要指向它的 OpenAI 兼容地址，例如 `http://<GATEWAY_HOST>:9080/new-api/v1`（经 APISIX）或受控内网地址。Java 的 `new-api.api-url` 与 `new-api.api-key` 同步使用该网关和平台专用令牌。

### 4.3 browser-api 浏览器服务

目录：`deploy/browser-api`

```bash
cd /srv/Axiom/deploy/browser-api
# 先编辑 .env；首次构建会下载 Playwright/Chromium
docker compose up -d --build
docker compose ps
./scripts/smoke_ws.sh   # 仅启动了 --profile ws 时执行
```

必须修改 [`.env`](../deploy/browser-api/.env)：

| 属性 | 配置要求 |
| --- | --- |
| `BROWSER_HOST_PORT` | 默认为 8089；跨主机部署时仅在内网发布。 |
| `MCP_ALLOWED_HOSTS` | 设置为实际访问主机名或 `<BROWSER_HOST>:8089`，不要长期保留 `*`。 |
| `BROWSER_EGRESS_PROXY` | 生产建议填写受控出口代理；代理应拒绝私网和元数据地址。 |
| `BROWSER_MEM_LIMIT` / `BROWSER_PIDS_LIMIT` / `BROWSER_SHM_SIZE` | 依据机器资源与并发调整；默认 4g / 4096 / 1gb。 |
| `BROWSER_WS_PATH` | 若启用可选 WS 端点，改为新的随机路径凭证。 |

agent-api 对应 [`.env`](../agent-api/.env) 的 `BROWSER_SERVICE_URL`：`http://<BROWSER_HOST>:8089/mcp`。同时在 browser-api 主机防火墙中只允许 `<AGENT_HOST>` 访问 8089。

### 4.4 OCR API

目录：`deploy/ocr-api`

```bash
cd /srv/Axiom/deploy/ocr-api
# 可选：创建 .env 并设置 OCR_TOKEN=<随机令牌>
docker compose up -d --build
docker compose ps
curl -fsS http://127.0.0.1:8088/health
```

需配置 [`docker-compose.yml`](../deploy/ocr-api/docker-compose.yml) 的 `OCR_TOKEN`（可选但推荐）。若配置令牌，平台管理端的 OCR API Key 必须填写相同值。

服务启动后，在前端“系统设置 → OCR”或调用 `PUT /agent-api/platform-config/ocr` 配置：`enabled=true`、`strategy=custom_endpoint`、`endpointUrl=http://<OCR_HOST>:8088/ocr`、`apiKey=<OCR_TOKEN>`。保存后使用“测试连接”验证。该 OCR 只处理图片；复杂图片理解应改用多模态模型策略。

### 4.5 websearch-api：搜索、抓取、重排

目录：`deploy/websearch-api`

```bash
cd /srv/Axiom/deploy/websearch-api
cp .env.example .env
# 编辑 .env，至少改 FIRECRAWL_PG_PASSWORD；按资源调整并发
# 同时将 searxng/settings.yml 的 secret_key 改为 openssl rand -hex 32 的输出
docker compose up -d
docker compose ps
docker compose logs -f ws-reranker-model-init

curl "http://127.0.0.1:8085/search?q=axiom&format=json"
curl -X POST http://127.0.0.1:8086/v1/scrape \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://example.com","formats":["markdown"]}'
curl -X POST http://127.0.0.1:8087/rerank \
  -H 'Content-Type: application/json' \
  -d '{"query":"测试","texts":["测试文本","无关文本"]}'
```

必须修改 [`.env`](../deploy/websearch-api/.env.example)（复制后形成 `.env`）中的 `FIRECRAWL_PG_PASSWORD`；可按内存调 `NUM_WORKERS_PER_QUEUE`、`MAX_CONCURRENT_JOBS`、`CRAWL_CONCURRENT_REQUESTS`。还必须修改 [`searxng/settings.yml`](../deploy/websearch-api/searxng/settings.yml) 的 `secret_key`。首次启动 `ws-reranker-model-init` 下载模型后显示 `Exited (0)` 是正常完成状态。

在 agent-api 的 `.env`/`.env.prod` 中配置：

```dotenv
WEB_SEARCH_ENABLED=true
WEB_SEARCH_SEARXNG_URL=http://<WEBSEARCH_HOST>:8085
WEB_SEARCH_FIRECRAWL_URL=http://<WEBSEARCH_HOST>:8086
WEB_SEARCH_LOCAL_RERANKER_URL=http://<WEBSEARCH_HOST>:8087
# 国内环境示例；以实际可用搜索引擎为准
WEB_SEARCH_SEARXNG_ENGINES=baidu,sogou,360search,quark,bing
```

也可在平台“联网搜索配置”页或 `PUT /agent-api/platform-config/web-search` 保存配置。当前 `platform/platform_config_service.py::get_web_search_config` 先读取保存值及默认值，再用非空的 `WEB_SEARCH_SEARXNG_URL`、`WEB_SEARCH_SEARXNG_ENGINES`、`WEB_SEARCH_SEARXNG_IMAGE_ENGINES` 覆盖对应字段；因此修改界面后仍访问旧搜索地址时，应先检查目标进程加载的这三项配置。其它字段按各自保存值/默认值合并，不能概括为所有环境变量都覆盖后台或反之。供应商池、`providerMode` 与 DeepSeek 官方检索开关也需按当前配置页设置；只填三个服务地址不代表每条检索路径已启用。8085–8087 仅允许 agent-api 主机访问。

### 4.6 OpenSandbox API

目录：`deploy/opensandbox-api`。必须在 agent-api 启动后执行，因为该 Compose 要加入 `agent-api_agent-network`。

```bash
# 先启动 agent-api，见第 6 节
cd /srv/Axiom/deploy/opensandbox-api
cp .env.example .env
# .env 中设置 OPENSANDBOX_SERVER_API_KEY=<随机强密钥>
docker pull opensandbox/execd:v1.0.21
docker pull opensandbox/egress:v1.1.5
docker compose up -d --build --force-recreate --remove-orphans
docker compose ps -a
curl -fsS http://127.0.0.1:8091/health
```

必须修改 [`.env`](../deploy/opensandbox-api/.env.example) 复制得到的 `.env` 中的 `OPENSANDBOX_SERVER_API_KEY`，并在 agent-api `.env` 中填入同一个值。按需复核 [`sandbox.toml`](../deploy/opensandbox-api/sandbox.toml)：`runtime.execd_image`、`docker.network_mode`、`docker.pids_limit`、`server.limit_concurrency` 和 egress 策略。不要删除 `drop_capabilities` 或 `no_new_privileges`。

agent-api 配置如下：

```dotenv
SKILL_SANDBOX_PROVIDER=opensandbox
SKILL_SANDBOX_OPENSANDBOX_DOMAIN=http://<OPENSANDBOX_HOST>:8091
SKILL_SANDBOX_OPENSANDBOX_API_KEY=<与 OpenSandbox 相同的密钥>
SKILL_SANDBOX_OPENSANDBOX_IMAGE=agent-sandbox-py:local
SKILL_SANDBOX_OPENSANDBOX_USE_SERVER_PROXY=true
SKILL_SANDBOX_OPENSANDBOX_CPU=1
SKILL_SANDBOX_OPENSANDBOX_MEMORY=1Gi
```

验收不能只看健康检查；从 agent-api 容器运行一次真实沙箱冒烟：

```bash
cd /srv/Axiom/agent-api
docker exec agent-api python scripts/sandbox_opensandbox_smoke.py
```

## 5. 可选：Ollama 本地向量模型

学校提供可用的云端向量模型时，直接在 New API 配置对应云端渠道即可，无需部署 Ollama。需要本地部署时，在 Linux 模型主机执行：

```bash
curl -fsSL https://ollama.com/install.sh | sh
ollama serve
ollama pull qwen3-embedding:0.6b
ollama list
curl http://127.0.0.1:11434/api/tags
```

将 Ollama 作为 New API 的渠道添加，渠道地址填写 `http://<OLLAMA_HOST>:11434`（同机 Docker 可用实际网关可达地址），模型为 `qwen3-embedding:0.6b`。然后在 agent-api `.env`/`.env.prod` 设置：

```dotenv
DEFAULT_EMBEDDING_MODEL=qwen3-embedding:0.6b
DEFAULT_EMBEDDING_DIMENSION=1024
```

若使用学校云端模型，以上两个值应改为云端渠道实际暴露的模型 ID 与维度。模型 ID、维度和既有 Qdrant collection 不一致时，需要按知识库迁移方案重建/重灌向量，不能混用旧向量。

## 6. 业务服务

### 6.1 Java 基础平台、鉴权、知识库、MinIO

本节是独立 Java 仓库的部署对接约定，Linux 示例路径为 `/srv/axiom-backend`。其 Compose、Spring Profile、属性名和 JAR 版本必须以该仓库当前文件为准，本次未读取或验证该仓库。

首先核对 Java 启动命令实际选择的 Spring Profile，再修改对应配置文件。例如使用 `prod` 时检查 `axiom-main/src/main/resources/application-prod.yml`；若部署方沿用 `campus`，则检查相应 Profile 文件。以下属性是对接检查项，不能作为当前 Java 实现已经核实的结论：

| 配置文件 | 属性 | 必填内容 |
| --- | --- | --- |
| `application-<profile>.yml` | `spring.datasource.dynamic.datasource.master` | MySQL JDBC URL、用户名、密码；库名与 agent-api `DATABASE_URL` 必须同为 `ai_boot`。 |
| 同上 | `spring.data.redis`、`axiom.redisson` | Redis 主机、端口、密码；Docker 内使用服务名 `redis`。 |
| 同上 | `axiom.minio` | `minio_url`、`minio_name`、`minio_pass`、`bucketName`；与 MinIO 管理员账户和目标桶一致。 |
| 同上 | `axiom.ai.knowledge.qdrant-url` | `http://<QDRANT_HOST>:6333`。 |
| 同上 | `axiom.apisix.base-url` / `api-key` | APISIX 管理地址和强管理密钥。 |
| 同上 | `axiom.gateway.identity-secret` | 与 agent-api `GATEWAY_IDENTITY_SECRET` 一致，用于网关身份签名验证。 |
| 同上 | `new-api.api-url` / `api-key` / `user-id` | New API 入口、平台专用令牌、平台用户 ID。 |
| `application.yml` 或选定 Profile | `management.endpoints.web.exposure.include` | 加入 `health`，以启用部署验收的 `/actuator/health`；不要因此向公网暴露管理端口。 |

再检查 Java 仓库根目录的 `docker-compose.yml`：配置 MySQL、Redis 和 MinIO 的生产账户信息，并使 Java Profile 与上一步的配置文件一致。MinIO 首次启动后，在 `http://<JAVA_HOST>:9099` 创建配置中的同名 bucket（例如 `ai-platform`）。

构建并启动：

```bash
cd /srv/axiom-backend
export JAVA_HOME=/opt/jdk-17
export PATH="$JAVA_HOME/bin:$PATH"
mvn clean package -DskipTests
cp axiom-main/target/axiom-main-3.9.1.jar ./axiom-main-3.9.1.jar
docker compose up -d
docker compose ps
curl -fsS http://127.0.0.1:9090/actuator/health
```

Jar 名称可能随 Maven 最终产物变化；执行 `ls axiom-main/target/*.jar` 后，确保它与 Compose 中 `app` 服务挂载和 `java -jar` 的文件名一致。

### 6.2 agent-api、Worker、Runtime PostgreSQL、Qdrant

目录：`agent-api`。生产 Compose 使用 `.env` 后再用 `.env.prod` 覆盖；不要把生产配置误写到 `.env.dev`。

必须配置 [`.env`](../agent-api/.env) / [`.env.prod`](../agent-api/.env.prod)：

| 属性 | 要求 |
| --- | --- |
| `DATABASE_URL` | 指向 Java 共用的 MySQL `ai_boot`，密码需 URL 编码。 |
| `CHECKPOINT_DATABASE_URL`、`RUNTIME_DATABASE_URL` | 分别配置 checkpointer 与 Runtime 的 PostgreSQL 库/连接池；可共用实例，Compose 内通常使用 `checkpoint-postgres:5432`。生产显式填写两项，不把“共用实例”理解为必须共用数据库。 |
| `QDRANT_URL` | Compose 内用 `http://qdrant:6333`；跨主机用实际内网地址。 |
| `NEWAPI_BASE_URL` | New API 的 `/v1` 兼容地址。 |
| `JAVA_INTERNAL_BASE` | Java 内网地址，用于 token 回源鉴权。 |
| `INTERNAL_SYNC_SECRET` | 与 Java 知识库 parser 配置一致。 |
| `AGENT_API_KEY_PEPPER` | 发布者 API Key 的独立 HMAC pepper；生产必须设置为随机强密钥并在所有 Agent API 副本保持一致。未设置时会兼容回退到 `INTERNAL_SYNC_SECRET`，不建议长期依赖该回退。 |
| `GATEWAY_IDENTITY_SECRET` | 与 Java/APISIX 的签名身份配置一致。 |
| `FILE_STORAGE_PROVIDER`、`MINIO_ENDPOINT`、`MINIO_ACCESS_KEY`、`MINIO_SECRET_KEY`、`FILE_STORAGE_BUCKET` | 指向第 6.1 节的 MinIO。 |
| `WEB_SEARCH_*`、`BROWSER_SERVICE_URL`、`SKILL_SANDBOX_OPENSANDBOX_*` | 使用第 4 节对应服务的内网地址和密钥。 |
| `USER_LOCATION_*` | 主对话按需的 IP 粗略定位开关、供应商、超时与缓存；默认供应商只适合小流量，上线前确认额度、出网和隐私政策，或替换为兼容的受控服务。 |
| `FORWARDED_ALLOW_IPS` | Uvicorn 只信这里列出的代理源 IP；须按线上 `X-Forwarded-For` 从右向左的链路，逐个列出 APISIX、Nginx 等所有受信 hop 的精确 IP（多个逗号分隔）。禁止为了定位设为 `*`，否则直连 8000 的客户端可伪造 `X-Forwarded-For`。 |
| `CONNECTOR_SECRET_KEY` | API 和独立 Worker 必须共用的加密主密钥；除连接器凭据外，活动 Run 的凭据与短期客户端 IP 也依赖它。不同密钥的新版 Worker 不会领取带该密钥标识的 Job，不能让两个容器各自生成本地密钥。 |
| `MIGRATE_ON_STARTUP` | 生产建议为 `false`，部署前按 `agent-api/migrations/README.md` 显式执行迁移。 |
| `RUNTIME_REQUIRED` | 生产设为 `true`，使 Runtime PG 不可用时服务拒绝就绪，而不是静默降级。 |

启动与验证：

```bash
cd /srv/Axiom/agent-api
# 首次或版本升级前，按 migrations/README.md 执行 MySQL 和 Runtime PG 迁移
docker compose up -d --build --force-recreate
docker compose ps
curl -fsS http://127.0.0.1:8000/health/ready
curl -fsS http://127.0.0.1:8000/docs >/dev/null
```

确认 `agent-api`、`agent-worker`、`agent-checkpoint-pg`、`agent-qdrant` 都正常运行后，再回到第 4.6 节启动 OpenSandbox。

当前源码迁移头为 MySQL `mysql_0015_work_folders`、Runtime `runtime_0020_workflow_results`。`MIGRATE_ON_STARTUP=false` 会比对版本并检查关键列；旧 Runtime 库不能靠启动时 `stamp head` 补齐。迁移步骤与环境加载行为见 [`迁移说明`](../agent-api/migrations/README.md)。作用域 Job 使用 `queued_scoped/leased_scoped`，升级时需协调 API 与全部 Worker 的版本；旧 Worker 不识别新状态，回滚前须处理这些在途任务。容器模式的 `/health/ready` 不负责证明独立 Worker 已能领取任务，还须检查 Worker 日志与真实新 Run。

## 7. 前端手动构建并使用系统 Nginx 部署

本节采用前端静态文件配合系统 Nginx 的部署方案。站点配置由部署方提供，示例目标文件为 `/etc/nginx/conf.d/axiom.conf`，静态文件目录为 `/var/www/html`。此前使用的外部 `nginx_conf` 不在本仓库内；不能把下表当作已核实的服务器现状，也不能据仓库里的其他 Nginx 示例直接覆盖线上配置。

此前部署约定中的关键转发关系如下，发布前须与实际 Nginx/APISIX 配置逐项核对：

| 请求路径 | 配置中的上游 |
| --- | --- |
| `/`、`/assets/`、`/js/`、`.mjs` | `/var/www/html` 下的前端构建产物 |
| `/api/` | `http://127.0.0.1:9090/`（Java） |
| `/agent-api/` | `http://127.0.0.1:9080/agent-api/agent-api/`（APISIX） |

注意：最后一条会把原始 `/agent-api/...` 请求转为上游的 `/agent-api/agent-api/...`。因此 APISIX 必须配置与该 URI 完全匹配的路由，或在 APISIX 侧将其重写为 agent-api 实际接收的 `/agent-api/...`；不要在未同步修改 APISIX 路由的情况下擅自改动 `nginx_conf`。

### 7.1 发布者自用 Agent API 与 iframe

智能体发布始终进入智能体广场。发布者可在“公开配置”中独立启用 OpenAI 兼容 API 和 iframe 嵌入；API Key 以 `qza_` 开头，只能由该智能体发布者创建和使用，模型调用与费用都归属发布者账号。不要把 Key 放入浏览器、iframe URL、前端配置或日志。

OpenAI 兼容入口为 `/agent-api/openai/v1`，模型别名为 `agent_<APP_ID>`。iframe 只支持静态嵌入：为一个精确 HTTPS 来源创建专用 `qze_` Key，生成的 URL 仅携带 `embedKeyId`，Key 明文必须置于 `#embedKey=...` fragment；fragment 不会作为 HTTP 请求、代理日志或 Referer 发出。`qze_` 只能换取该应用的短时 iframe 会话，不能调用 OpenAI 接口或管理 API；泄露后仍可消耗该应用额度，应按来源分别创建并可随时撤销。不得把 `qza_` API Key 放进 iframe。

`deploy/nginx_conf` 为 frame 路径设置了单独的反向代理位置：该位置不能发送全局 `X-Frame-Options: SAMEORIGIN`，由 Agent API 返回精确的 `Content-Security-Policy: frame-ancestors <登记来源>`。部署后必须验证：

```bash
curl -I 'https://<FRONTEND_HOST>/agent-api/embed/v1/frame/<APP_ID>?embedKeyId=<PUBLIC_EMBED_KEY_ID>'
```

响应应包含 `Cache-Control: no-store`、`Referrer-Policy: no-referrer` 及不含通配符的 `frame-ancestors`；不应包含 `X-Frame-Options: SAMEORIGIN`。

部署操作：

```bash
# 1) 在构建机生成静态文件
cd /srv/Axiom
pnpm install --frozen-lockfile
pnpm build

# 2) 将 nginx_conf 上传到部署机后安装为唯一的站点默认配置
sudo install -D -m 0644 /srv/Axiom/nginx_conf \
  /etc/nginx/conf.d/axiom.conf
# 确认 Nginx 没有同时启用第二份 listen 80 default_server 的默认站点配置。

# 3) 发布构建产物（发布前按运维策略备份现有 /var/www/html）
sudo install -d -m 0755 /var/www/html
sudo rsync -a --delete dist/ /var/www/html/
sudo nginx -t
sudo systemctl reload nginx
```

执行上面的安装命令前，先将部署方确认的站点配置放到 `/srv/Axiom/nginx_conf`，并核对静态目录与上游路径。发布完成后，用第 8 节的 `/agent-api/models` 检查确认响应是 JSON 而非 SPA 的 HTML。

## 8. 最终验收清单

```bash
# 组件服务
curl -fsS http://<GATEWAY_HOST>:9080/health || true
curl -fsS http://<NEWAPI_HOST>:3001/api/status
curl -fsS http://<OCR_HOST>:8088/health
curl -fsS http://<OPENSANDBOX_HOST>:8091/health
curl -fsS "http://<WEBSEARCH_HOST>:8085/search?q=health&format=json" >/dev/null

# 业务服务
curl -fsS http://<JAVA_HOST>:9090/actuator/health
curl -fsS http://<AGENT_HOST>:8000/health/ready
curl -s http://<FRONTEND_HOST>/agent-api/models | head -c 160
```

最后一条应返回 JSON（未携带 token 时通常是“缺少访问令牌”），不能是 `<!doctype html>`。随后以真实账号登录，依次验证：模型列表、一次普通对话、知识库上传/检索、OCR 图片上传、联网搜索、浏览器工具和沙箱执行。发生异常时先看对应 `docker compose logs --tail=200 <service>`，再核对本手册中的地址、端口、密钥和 APISIX 路由是否一致。
